# LOCALKAAM PROJECT - BUG REPORT

## Critical Issues (High Priority)

### 1. **DUPLICATE FUNCTION DEFINITION - `accept_quotation()` (CRITICAL)**
**Location:** `accounts/views.py:123` and `accounts/views.py:565`

**Issue:** The function `accept_quotation()` is defined twice in the same file. This causes the second definition to override the first one, potentially breaking functionality.

**Impact:** 
- The first definition (line 123) will never be executed
- Only the second definition (line 565) will be active
- This could lead to unexpected behavior if both had different logic

**Code:**
```python
# Line 123 - First definition
@login_required
def accept_quotation(request, quotation_id):
    if request.user.role != "customer":
        return redirect("dashboard")
    # ... logic here ...

# Line 565 - Second definition (overrides first)
@login_required
def accept_quotation(request, quotation_id):
    if request.user.role != "customer":
        return redirect("dashboard")
    # ... similar logic here ...
```

**Recommendation:** Remove one of the duplicate functions. They appear to have identical implementations and only one should exist.

### 2. **RATE LIMITER INEFFECTIVE - Allows Requests When Limited (CRITICAL)**
**Location:** `accounts/utils.py:47-77`

**Issue:** The rate limiter decorator returns the view function even when the user is rate limited. Line 72 calls `return view_func(request, *args, **kwargs)` after rate limiting, allowing the request to proceed.

**Code:**
```python
def rate_limit(key_prefix, max_attempts=5, timeout=300):
    def decorator(view_func):
        @wraps(view_func)
        def wrapper(request, *args, **kwargs):
            if not settings.DEBUG:
                ip = request.META.get("REMOTE_ADDR", "unknown")
                key = f"{key_prefix}:{ip}"
                is_limited, remaining = rate_limiter.is_rate_limited(
                    key, max_attempts, timeout
                )
                if is_limited:
                    if request.headers.get("Accept") == "application/json":
                        return JsonResponse(...)
                    from django.contrib import messages
                    messages.error(request, f"Too many attempts...")
                    return view_func(request, *args, **kwargs)  # BUG: Should NOT proceed here!
            return view_func(request, *args, **kwargs)
        return wrapper
    return decorator
```

**Impact:**
- Rate limiting is completely ineffective
- Users can bypass attempt limits by repeatedly sending requests
- Login brute-force attacks are possible despite rate limiting
- Password reset and registration can be abused

**Recommendation:** Replace `return view_func(request, *args, **kwargs)` with a redirect to the same page or an error response like:
```python
return redirect(request.path)  # or return HttpResponseForbidden()
```

### 3. **INSECURE USERNAME GENERATION - Email Prefix Used as Username (HIGH)**
**Location:** `accounts/forms.py:53-58` and `accounts/models.py:27-28`

**Issue:** The username is generated by splitting the email at "@" and taking the prefix:
```python
user.username = user.email.split("@")[0]
```

**Problem:**
- If two users have the same email prefix (e.g., john.smith@gmail.com and john.smith@yahoo.com), the second registration will fail with integrity error because `username` field must be unique
- This creates unpredictable behavior
- Security concern: Email prefixes can be easily guessed

**Impact:**
- Registration failures for valid users
- Potential security vulnerability

**Recommendation:** Generate a unique username using UUID or a random string instead:
```python
user.username = f"user_{uuid.uuid4().hex[:12]}"
```

## Major Issues (Medium-High Priority)

### 5. **RATE LIMITER NOT PRODUCTION-READY - In-Memory Cache Without Persistence**
**Location:** `accounts/utils.py:15-44`

**Issue:** The rate limiter uses an in-memory dictionary:
```python
class RateLimiter:
    def __init__(self):
        self._cache = {}
```

**Problems:**
- Data is lost when the server restarts
- In multi-server deployments, each server has its own cache - limiting won't work across servers
- No synchronization between worker processes

**Impact:**
- Rate limiting is ineffective in production environments with multiple servers
- Users can bypass limits by targeting different server instances

**Recommendation:** Use Redis or Memcached for shared rate limiting:
```python
from django.core.cache import cache
# Use cache.get/set instead of self._cache
```

```python
urlpatterns += static(settings.STATIC_URL, document_root=settings.STATICFILES_DIRS)
```

`STATICFILES_DIRS` is a list, not a directory path. This should be `STATIC_ROOT`.

### 7. **NO TRANSACTION HANDLING FOR CRITICAL OPERATIONS (MEDIUM)**
**Location:** `accounts/views.py:123-161` (accept_quotation function)

**Issue:** When accepting a quotation, multiple database updates occur without transaction protection:
1. Update quotation status to "accepted"
2. Update job with worker and status
3. Reject other quotations
4. Delete availability

**Code:**
```python
quotation.status = "accepted"
quotation.save()

job = quotation.job
job.worker = worker
job.status = "confirmed"
job.save()

Quotation.objects.filter(job=job).exclude(id=quotation_id).update(status="rejected")

Availability.objects.filter(
    worker=worker, date=job_date, time_slot=job_time_slot
).delete()
```

**Impact:**
- If a failure occurs mid-operation, database will be in inconsistent state
- Partial transactions could leave orphaned records

**Recommendation:** Use `@transaction.atomic()` decorator:
```python
from django.db import transaction

@transaction.atomic()
def accept_quotation(request, quotation_id):
    # ... rest of the code
```
